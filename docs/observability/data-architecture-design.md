## 2. Normalization & relationship rules for new columns/table

1. **Ownership XOR everywhere.** `scores` mirrors `prompt_logging_settings:34-38` (`CHECK ((user_id IS NULL) != (org_id IS NULL))`) + the two partial live-UQs pattern (per-scope uniqueness where applicable). Ledger correlation columns (`trace_id`, `session_key`) are stamped from the *resolved setting's scope* at capture (same pattern as `capture.py:78-90`), never from caller hints (Agent 3 §4.1 independence).
2. **Append-only rows have no soft-delete.** Precedent: `PromptLog(TimestampedModel)` and `GuardrailTrigger(TimestampedModel)` carry no `is_deleted` — immutable by design. `scores` follows suit (corrections are new rows, except the same-`(name, subject, date)` rewrite).
3. **Explicit FK + `relationship` + `back_populates`, metadata-declared partial indexes** (backend.md: `alembic check` stays green). Every FK gets an index — verified live that all six `prompt_logs` FKs are indexed (composite `(fk, created_at)` covers the FK check).
4. **`generation_id` FK (recommended).** Live constraint dump confirms `prompt_logs.generation_id` is a **bare UUID with no FK** (all other UUID refs have FKs). Internal-plane invariant is `generation_id == messages.id` (`message.py:26-32`, `generation.py:548-560`). Recommend adding `FK → messages.id ON DELETE SET NULL` + btree index: makes generation→ledger joins trustworthy, costs nothing on the public plane (NULLs), and account-purge hard-deletes of messages degrade to NULL links instead of dangling ids. (If the orchestrator prefers zero DDL, the alternative is documenting the logical link — but the FK is cheap and this is exactly the join Agents 2/F7 need.)
5. **`request_id` stays a string, types stay un-unified.** Public plane writes uuid4-hex per request; internal plane reuses one `key_request_id` per conversation across generations (hence the composite dedup key, §7). Do not coerce to UUID — legacy rows and cross-plane divergence make a type migration high-risk for zero query gain.
6. **NULL means unknown, never zero.** New usage/cost/`usage_estimated` columns are **nullable with no server default for history** (application writes non-null for new rows). Precedent for the danger: unpriced models bill silent `$0` today (Agent 2 §9 P2) — the ledger must not repeat that lie. `NULL cost` = unpriced/unknown; `NULL usage_estimated` = pre-migration row (unknowable, Agent 2 §8); never backfill `false`/`0` over history.
7. **Reserved span shape (E4 gate, no DDL now).** When tool-call persistence ships: `observation_spans(id, trace_id, parent_observation_id NULL-able, observation_type, name, started_at, ended_at, level, status_message, input_ref, output_ref, workspace XOR, created_at)` with `(trace_id, created_at)` + `(parent_observation_id)` indexes. Written here so the future writer needs no redesign — not created now.

### 3.3 Redundant indexes to drop (write amplification on the capture hot path)

`request_logs` carries three pairs where the composite prefix already covers the single-col index: `(conversation_id, created_at)` ⊃ `(conversation_id)` (`ix_request_logs_conversation` vs `ix_request_logs_conversation_id`); `(user_id, created_at)` ⊃ `(user_id)`; `(api_key_id, created_at)` ⊃ `(api_key_id)`. Every capture-path INSERT pays per index (prompt_logs 12, request_logs 14, messages 13 indexes today). Drop the three singles in a low-traffic migration (I-drop: index drop takes `ACCESS EXCLUSIVE` briefly — trivial at current sizes, schedule off-peak at scale; zero data loss, planner-verified redundant for both the purge-by-`user_id` and lookup paths). Keep all `prompt_logs` indexes — no redundancy found there.

### 3.4 Tag/metadata GIN rule (no indiscriminate JSON indexing)

No `tags`/`metadata` columns are proposed in §8 (closed schema holds until a proven query needs them). When they arrive: **(a)** `tags TEXT[]` → `USING gin (tags)` (array ops, not trgm); **(b)** `metadata JSONB` → `USING gin (metadata jsonb_path_ops)` scoped to documented top-level keys, or per-key expression/btree indexes for the 2–3 keys actually filtered — **never** a bare `USING gin (metadata)` default-ops index (forbes arbitrary `@>` shapes, bloats every write, and the bodies-live-elsewhere design means metadata stays small but hot). Each GIN needs a named query in the migration comment as evidence. `Message.metadata_` gets no GIN (media-details bag, never filtered — verified no index live, correctly).

## 4. Ingestion / queue behavior (as built; design constraints for new writers)

Current path (verified `queue.py`, `capture.py`, `resolution.py`): policy resolution + 512K-char truncation + Fernet encryption run **synchronously at enqueue** (`build_row_kwargs`), so raw content never crosses threads; payloads are immutable by the time the single background worker persists with its own Sessions (SQLAlchemy sessions never leave their thread — the `capture_post_async`/`_capture_fresh` bridges preserve this). Bounded `MAXSIZE=1000` (`put_nowait` → drop + `dropped_full` counter + warn, ids-only in logs); worker does 1 retry then drop + `_last_error` (exception class only) surfaced in `retention_info`; worker-down → **inline sync fallback** on the caller's session (fail-open, never fail-silent); idempotency via partial-UQ collapses redeliveries (`IntegrityError` → `duplicate` counter, never re-raised); Valkey counters 90-day TTL; skipped-under-pytest with explicit `start_for_tests` seam.

Design assessment (constraints any new capture writer must preserve):

1. **Fail-open is load-bearing, keep it.** Generation paths never block on the ledger (`enqueue_post` never raises; bridges return `skipped` on timeout). The `scores` writer (E6) MUST use the same `enqueue_post`-style path (bounded queue + sync fallback), never inline INSERT on the request path.
2. **Backpressure is counted, not alerted (P2, Agent 2 §15).** Sustained >1000-deep bursts lose ledger rows with only a Valkey counter + log line as witness. Design rule: any dashboard/alerting work reads `queue.stats()` (`queue_depth`, `dropped_full`, `dropped_error`, `duplicates`, `last_error` — already exposed via `retention_info`) and pages on `dropped_* > 0`; do not grow `MAXSIZE` to "fix" drops (unbounded memory on the request path is worse than counted loss). No DLQ: drops are policy-skips/duplicates/error-rows by class, and a DLQ for `dropped_error` alone is YAGNI until error-drops are proven non-transient.
3. **Double-resolution waste (P3, found in this audit).** `enqueue_post` calls `build_row_kwargs` (policy reads + 2× Fernet encrypts), then the worker-down fallback calls `capture_post` → `build_row_kwargs` **again** (repeat policy SELECTs + repeat encryption). Harmless when the worker runs (payload reused), wasteful exactly when degraded. Fix (Phase 2, backend): `capture_post` accepts a prebuilt payload (`capture_post_prebuilt(db, row_kwargs)`); `enqueue_post` passes its payload through instead of re-resolving.
4. **Hot-path read cost is the real overhead.** `resolve_setting` does up to ~5 sequential SELECTs per generation (provenance key lookup, user + org zero-retention checks, live setting, key targets, override/liveness) *even when logging is disabled* — the ledger is default-off, so the common case pays resolution for a `None`. At current volume this is noise; if profiling ever flags it, cache live settings keyed by `(scope, id, version)` with short TTL + invalidation on upsert — explicitly NOT proposed now (correctness risk > measured cost).
5. **One worker thread is enough.** Ordering per connection is not required (idempotent collapses), throughput is one small INSERT per generation. Do not shard workers without evidence; batch (`add_all` + single commit per drain) is the first lever if the worker ever lags.

## 5. Retention cleanup + purge performance

1. **Retention sweep must be batched (P1 at scale).** `expire_due_logs` is one unbounded `UPDATE … WHERE expires_at < now AND content_expired = false` (`retention.py:29-37`) — one transaction holding row locks on *all* due rows, one commit, and one dead-tuple per row for autovacuum. Correct at today's volume; at 10M+ rows a daily spike becomes a long lock + replication lag + bloat wave. Design: `UPDATE … WHERE id IN (SELECT id … LIMIT 5000)` loop with per-batch commit, ordered by `expires_at` using I1; log per-batch counts (same logger, no per-org ledger — accepted gap M3 stands).
2. **User-invoked `purge_logs` same treatment.** Unbounded `UPDATE … WHERE created_at < cutoff` per workspace (`records.py:341-353`) — add the same LIMIT-loop when any workspace exceeds ~100K rows; org path already writes the `_audit` row per call (keep: one audit row per purge invocation, not per batch).
3. **Account purge: commit per table.** The scheduler purge issues ~10 sequential `DELETE … WHERE user_id` across ledgers/settings/logs (`scheduler.py:216-250`); keep per-table commits (never wrap the whole account in one transaction) and keep `PurgeAuditLog` last with the existing success/failure + counts semantics — it has no FK to `users` by design (user row is gone) and that stays.
4. **`expires_at` is stamped once, never restamped (keep).** Later setting changes do not re-stamp rows; only sweep + explicit purge apply (Agent 2 §11, Agent 3 §2.4). Do NOT "fix" by restamping on setting change — retroactively extending/shrinking retention on stored rows is a legal-footgun, not a bug. The frontend one-line copy (Agent 4 F10) is the correct remedy.
5. **Metadata-forever is the documented contract.** Rows are never deleted by retention; only ciphers NULL. Any future true-delete (e.g. regulated `hard_delete_after_days`) is a NEW explicit policy + migration, not a reinterpretation of `retention_days`.

## 6. Search / analytics query scalability

1. **Listing shape is already scalable.** Cursor keyset `(created_at, id)` (`records.py:230-244`) + scope-prefix composites + batched enrichment (4× one-per-page lookups, no N+1, `records.py:99-142`) — keep this exact pattern for scores/export listings. The one inconsistency: request-log listing uses offset paging (`api/request_logs/router.py`) — migrate it to the same keyset cursor when its filters are next touched (offset degrades linearly; keyset is proven in-tree).
2. **`q` search is a scoped scan by construction.** `request_id ILIKE '%…%'` (escaped, ≤128 chars, `records.py:227-229`) has a leading wildcard — no btree can serve it; within a workspace scope this is acceptable to mid-scale. If it ever dominates: `pg_trgm` GIN on `request_id` (justified *then* by slow-query evidence), or split exact-match (`=`) onto the existing btree first. Cross-type search (`search/groups.py:110-121`) adds `endpoint ILIKE` — same rule.
3. **IO is unsearchable by design — keep it that way.** Bodies are Fernet ciphertext (`core/crypto.py:17-18`); any "full-text over prompts" request requires a purpose-built plaintext index pipeline with its own retention/redaction story, not decryption-at-query. The correct answer to that request is E5-events with excerpt columns, not searchable ciphers.
4. **Analytics aggregates need no rollups yet.** Server-side aggregates over `request_logs`/`api_request_logs` are full scans per query — fine at tens of rows, and the per-(user/role/model/key)-composites serve the common GROUP cuts. Add daily per-(org, model) rollup/materialized aggregates only on slow-query evidence, never pre-emptively (a rollup pipeline is a second writer with its own consistency story).
5. **Range filters wait on columns.** Tokens/cost/latency numeric filters (Agent 4 F8) are impossible until §8 M-a lands; when they do, each filter ships with its §3.2 composite in the same migration (filter + index atomically, or neither).

## 7. Idempotency (`request_id` + `generation_id` unique semantics — keep, extend carefully)

Live: partial-UQ `uq_prompt_logs_request_delivery (request_id, generation_id) WHERE request_id IS NOT NULL` (model comment `prompt_logging.py:148-160`, migration `m2n3o4p5q6r7`). Verified semantics: internal plane reuses one `key_request_id` per conversation across generations, so bare-`request_id` uniqueness would brick the migration and drop legitimate rows — the composite is load-bearing, not incidental. Public plane sends `generation_id=None` with uuid4 `request_id`s (`public_gateway/service.py:747-774`): dedup degrades to request_id-only, which is safe (uuid4s never collide across distinct requests) but means a same-request redelivery with `generation_id=None` dedups while legacy `request_id IS NULL` rows stay exempt (documented). Worker/bridge races (async thread + worker both persisting) are collapsed by the UQ into `duplicate` counts — the counter conflates true redeliveries with races; acceptable, do not "fix" by removing the backstop. When `trace_id` (E1) lands: **do not** extend the UQ to `(trace_id, generation_id)` unless a writer can produce colliding `trace_id`s across distinct operations — new key, same rule: uniqueness must match the actual redelivery unit, or it becomes a data-loss mechanism. Default: keep the existing UQ untouched.

## 8. Migration plan outline (historical `prompt_logs` safety)

Precedent reviewed: `j4k5` (create), `k5l6` (additive index), `m2n3` (additive col/table + partial-UQ with data-aware comment), `q6r7` (drop team targets + `team_ids` column: rows preserved, `match_source='team'` left readable, downgrade recreates empty). Follow the `q6r7` contract for anything destructive: **remap + preserve rows, never rewrite history.**

- **M-a (P0, Agent 2 §§8–9): `prompt_logs` usage/cost/estimate columns.** Additive nullable, no server defaults (metadata-only DDL, no table rewrite): `total_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens` (Integer NULL); `input_cost`, `output_cost`, `total_cost` (Numeric(12,8) NULL — same precision as `messages`, *not* `api_request_logs`' (14,8): ledger precision must match the generation source it joins); `usage_estimated` (Boolean NULL; app writes non-null for new rows; NULL = pre-migration unknown, §2.6); `capture.build_row_kwargs` forwards full token map + costs (both planes already compute them — `generation.py:558` passes only `{prompt, completion}` today, the rest is dropped at the call site). Downgrade: drop columns (values re-derivable from `messages`/`request_logs` joins — state this in the migration comment).
- **M-b (correlation + diagnostics):** `trace_id` (Text NULL), `session_key` (Text NULL), `prompt_name`/`prompt_version`, `level` (String(8) NULL — no default; unset ≠ DEFAULT is a Langfuse semantic worth preserving), `status_message` (Text NULL), `ttfb_ms` (Float NULL, public plane backfill only where measurable), `model_params` deferred to `messages`-only (ledger does not need a third copy of settings). Same additive/nullable shape; downgrade drops cleanly.
- **M-c (E6): `scores` table** + I4 indexes + XOR check + partial live-UQs, all metadata-declared (backend.md `alembic check`). Downgrade drops the table — **flag as destructive in review**: scores are human/machine judgments, not re-derivable. Require explicit orchestrator approval; default is forward-only after merge.
- **M-d (index hygiene):** I1 (create partial `CONCURRENTLY`, then drop old `ix_prompt_logs_expires`), I2, drop the three redundant `request_logs` singles (§3.3). `CONCURRENTLY` cannot run inside a transaction — separate `op.execute(..., execution_options={"autocommit": True})` / offline `CREATE INDEX CONCURRENTLY` + `alembic check` reconciliation per backend.md, never in the M-a/M-b transaction.
- **Backfill (online, batched, honest NULLs):** internal rows join `messages` on `generation_id = messages.id` for tokens/costs/`usage_estimated`; public rows join `api_request_logs` on `request_id`; unjoinable/legacy rows stay NULL (never `0`/`false`). Batch `UPDATE … WHERE id IN (SELECT id … LIMIT 5000)` with per-batch commit + `pg_sleep`-free throttle via the worker pattern; **never restamp `expires_at`** (§5.4). `trace_id` backfill: internal `= generation_id`, public `= request_id`; `session_key` backfill: none (NULL = pre-correlation era).
- **What is NOT migrated:** bodies stay Fernet (no re-encryption rotation in this plan); `match_source='team'` legacy values stay readable (q6r7 contract); no renames anywhere (no sweep needed); `retention_policies`/`export_events` untouched (authz/API work, not DDL).

## 9. Performance baseline notes (cheap read-only probes only — no load tests, no destructive tests)

- **Scale today (planner estimates, `pg_class.reltuples`):** `conversations` 30, `messages` 54 rows; `prompt_logs` / `request_logs` / `api_request_logs` / `guardrail_triggers` all `-1` (empty or never vacuumed/analyzed — i.e. effectively zero). Total relation sizes 80–290 KB. All "plans" below are structural, not load evidence — stated so Phase 2 does not mistake them for benchmarks.
- **Listing (hot read):** org-scoped keyset page resolves to `Index Scan Backward using ix_prompt_logs_org_created` (bare `EXPLAIN`, §3.1) — optimal; cost driver at scale will be the `q` leading-wildcard scan (§6.2) and enrichment fan-out (bounded: 4 queries/page regardless of limit).
- **Retention sweep (daily write):** seq-scan plan is correct *now* (tiny table, full `ix_prompt_logs_expires` unused by the planner); I1 (§3.2) is the ahead-of-scale fix. Per-row cost is one narrow `UPDATE` NULL-ing two TOAST-able ciphers — TOAST churn + dead tuples per expired row; batching (§5.1) bounds transaction size, autovacuum handles the rest (no tuning proposed without evidence).
- **Sync capture overhead per generation (code-derived, not measured):** ~5 sequential policy SELECTs (worst case) + up to 2× Fernet encrypt of ≤512 KB bodies + `put_nowait`. Dominant term is encryption on large bodies, not the queue (mutex + `put_nowait` is nanoseconds). The inline-fallback path doubles encryption (§4.3) — the only concrete waste found.
- **Write amplification:** each ledger INSERT pays 12–14 index writes (§3.3); the §3.3 drops remove 3 from `request_logs`. No fillfactor/GIN/autovacuum tuning proposed — unjustified at this size and explicitly YAGNI.
- **Analytics/export reads:** full-scan aggregates + cursor-paged exports are linear and fine; revisit with `pg_stat_statements` slow-query evidence only. No `ANALYZE`/stats changes made (read-only probes left no footprint).
